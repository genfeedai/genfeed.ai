# MCP Server

Your Genfeed instance runs an MCP server that gives your agent permission-scoped
access to content, workflows, publishing, analytics, and ads. It starts with the
rest of the stack; no extra install is needed.

**Endpoint:** `http://localhost:3014/mcp` on a default install. If you run behind
your own domain, use that MCP URL instead (see
[Reverse Proxy and HTTPS](/self-host/reverse-proxy)).

**Transport:** Streamable HTTP, MCP revision `2026-07-28`, with stateless
compatibility for 2025-era clients. Modern requests carry their protocol version,
client identity and capabilities in `params._meta`, together with the
`MCP-Protocol-Version`, `Mcp-Method` and (where applicable) `Mcp-Name` headers.
They can call tools directly without `initialize` or a session ID. `server/discover`
provides optional server metadata and requires authorization, just like the
legacy `initialize` handshake. Legacy clients continue to use their existing
handshake on the same endpoint.

**Authentication:** a scoped API key from your instance, or browser OAuth where
your client supports it. See [Authentication](#authentication).

Examples on this page use the default local address. Replace
`http://localhost:3014` with your MCP origin and `http://localhost:3010` with your
API origin if they differ.

## Connect to your instance

Start your stack first (see [Installation Options](/self-host/installation)),
then connect a client.

### Claude Code

Register the dedicated content connector, then open `/mcp` inside Claude Code,
select `genfeed`, and complete browser OAuth:

```bash
claude mcp add --transport http genfeed --scope user http://localhost:3014/mcp/claude
```

This connector does not generate media. To generate images, video and audio
from Claude Code, add the standard endpoint as a second server:

```bash
claude mcp add --transport http genfeed-media --scope user http://localhost:3014/mcp
```

Configure your deployment's public app, API, and MCP URLs so OAuth discovery
points at addresses your browser can reach; see
[Configuration](/self-host/configuration#public-urls).

### Codex and other clients

Point the client at the standard `http://localhost:3014/mcp` endpoint with a
scoped API key. Create the key in your web app under **Settings → API keys**
using the **MCP** preset (for the default seeded organization,
`http://localhost:3000/default/~/connectors/api-keys`), or use the guided
**Agents** section of Connectors (`/connectors/agents`) in your web app, which creates an MCP-scoped key
and runs a verification check. Export the key in the MCP client's environment,
not in the Genfeed container's `.env`:

```bash
export GENFEED_API_KEY=gf_live_xxx
codex mcp add genfeed --url 'http://localhost:3014/mcp' --bearer-token-env-var GENFEED_API_KEY
```

To enter the key without putting its value in shell history:

```bash
read -s GENFEED_API_KEY && export GENFEED_API_KEY
```

Codex reads the named environment variable. Do not paste credentials into
chats, commits, or shared logs. Inspect and update an existing Genfeed server
entry before switching authentication methods; preserve unrelated servers.

You can also add the server in your user-level `~/.codex/config.toml`:

```toml
[mcp_servers.genfeed]
url = "http://localhost:3014/mcp"
bearer_token_env_var = "GENFEED_API_KEY"
```

In any other client that supports remote Streamable HTTP, add the endpoint as a
custom MCP server and supply the key as a bearer token. Genfeed uses standard
discovery, registration, and PKCE flows for OAuth, so compatible clients can
authorize in the browser instead, but each client still needs a verification run
on your deployment. Source compatibility does not establish that a given
client's OAuth, reconnect, or media flows work.

### Verify access

Ask your agent: **"List my Genfeed brands."** A successful scoped read verifies
access. `codex mcp list` or `claude mcp list` can diagnose configuration, but a
server entry or copied command alone does not prove authorization.

If consent is denied or the login expires, restart authorization through
`codex mcp login genfeed` or Claude Code's `/mcp`. Check the account and
organization on the consent screen. Revoke unwanted access from your instance's
API key settings.

Client syntax was checked against Codex CLI 0.153.2 (`mcp add --help` and
`mcp login --help`) and the [Claude Code MCP documentation](https://code.claude.com/docs/en/mcp).

## Authentication

Turning off the web login wall (`BETTER_AUTH_ENABLED=false`) does not disable MCP
authentication: the standard `/mcp` endpoint still requires a bearer token. See
[Configuration](/self-host/configuration#login-wall). Authenticated requests
carry either an API key you created or an access token managed by an OAuth
client:

```http
Authorization: Bearer <api-key-or-access-token>
```

Missing, invalid, or expired tokens return 401 errors. An OAuth client should
use its refresh token on a 401 before restarting browser authorization. Keys
remain copy-once; see [API Keys](/api-reference/api-keys) for scopes, rotation,
and revocation. Use the **MCP** preset, which is approval-first and excludes
direct publishing.

The endpoint accepts `POST`, `GET`, and `DELETE`.

### OAuth conformance

What a spec-compliant client can rely on:

- **Discovery (RFC 9728).** Protected-resource metadata is served at both
  `http://localhost:3014/.well-known/oauth-protected-resource` and the
  path-suffixed `.../oauth-protected-resource/mcp`, with identical bodies. A
  `401` from `/mcp` carries a `WWW-Authenticate` header pointing at that
  metadata. Authorization-server metadata is served by your API at
  `http://localhost:3010/.well-known/oauth-authorization-server`. Both documents
  are readable cross-origin.
- **Resource identifier (RFC 8707).** The `resource` is your MCP URL ending in
  `/mcp` for the standard connector, or `/mcp/claude` for Claude. Claude
  discovery is at `/.well-known/oauth-protected-resource/mcp/claude`. Send it on
  the authorize and token requests.
- **Client metadata documents (CIMD).** A public client can use its HTTPS
  metadata-document URL as `client_id`, without registering first. The document
  must have a path and contain the exact `client_id`, `client_name` and
  `redirect_uris`; only public PKCE clients (`token_endpoint_auth_method: none`)
  are supported. Fetches require public HTTPS destinations, refuse redirects,
  time out after five seconds and accept at most 64 KiB of JSON. Valid metadata
  is cached for at most five minutes; `no-store` and `no-cache` disable caching.
  Discovery advertises `client_id_metadata_document_supported: true`.
- **Legacy registration (RFC 7591).** `POST /v1/oauth/register` with `redirect_uris`;
  `token_endpoint_auth_method` is `none`.
- **Authorization.** `code_challenge_method` must be `S256`. `state` is
  optional; when supplied it is echoed unchanged on both the success and the
  `access_denied` redirect. Both redirects include `iss` equal to the issuer
  advertised by authorization-server metadata; clients must validate it before
  exchanging a code (RFC 9207). Discovery advertises
  `authorization_response_iss_parameter_supported: true`.
- **Tokens.** The token exchange returns an access token and a
  `refresh_token`. Access tokens expire after 30 days. Present the refresh
  token with `grant_type=refresh_token` to obtain a new access token without a
  second consent screen; each refresh rotates the refresh token, and reuse of a
  consumed refresh token revokes the whole chain. A narrower `scope` may be
  requested on refresh; a wider one is rejected.
- **Revocation (RFC 7009).** `POST /v1/oauth/revoke` with the refresh token
  ends the connection. Revoking the key from your instance's API key settings
  has the same effect.
- **Enterprise-managed authorization (jwt-bearer).** An organization owner can
  let their identity provider, or Claude itself, sign members in without a
  consent screen. Discovery lists
  `urn:ietf:params:oauth:grant-type:jwt-bearer` in `grant_types_supported`. See
  [Enterprise-managed authorization](#enterprise-managed-authorization).


### Enterprise-managed authorization

Enterprise-managed authorization lets a member of your organization use the
Genfeed connector without a consent screen. The client sends a signed identity
assertion (an ID-JAG, `typ` `oauth-id-jag+jwt`) to the token endpoint with the
RFC 7523 `jwt-bearer` grant and gets an access token back. It is available
only to clients whose metadata document declares the `jwt-bearer` grant, such
as the Claude connector; dynamically registered clients cannot use it.

Set it up as the organization owner:

1. Read your values: `GET /v1/organizations/{organizationId}/settings/mcp-enterprise-auth`
   returns the `tenantId` (your organization id), the `audience` (the issuer
   the assertion must be addressed to), the `resource` and the `tokenEndpoint`.
2. Register the issuer that signs your assertions: `PUT` the same path with
   `{ "isEnabled": true, "trustedIssuer": "<issuer URL>" }`. For an identity
   provider this is its issuer URL; for assertions signed by Claude it is
   `https://identity.anthropic.com/issuers/<issuer-id>`. Enter the issuer
   exactly as it signs, trailing slash included.
3. Enter the `tenantId` as the tenant id in the connector settings so the
   assertion names your organization (`aud_tenant`). Without it the issuer
   must belong to exactly one Genfeed organization.

`DELETE` on the same path removes the setup. Only organization owners (and
platform superadmins) can read or change it, because whoever controls the
trusted issuer can sign in as any member of the organization.

What the token endpoint checks, in order, refusing anything else with
`invalid_grant`:

- the issuer is registered and enabled for one organization (or `aud_tenant`
  names the organization registered for it);
- the signature verifies against keys published at the issuer's
  `/.well-known/openid-configuration` `jwks_uri` (ES256 or RS256 only, never
  keys named in the assertion itself) and `typ` is `oauth-id-jag+jwt`;
- `aud` is exactly this server's issuer, and `client_id` matches the request;
- `exp`, `iat` and `nbf` hold within 60 seconds of skew, and the assertion
  does not outlive an hour;
- the assertion carries `sub`, `jti` and `email`, and has no `cnf` claim
  (sender-constrained assertions are not supported);
- the `email` belongs to an active, verified member of that organization. No
  account is created and `sub` is not used to find the member;
- the `jti` has not been used before for that issuer.

The access token is bound to that member and organization, uses the member's
current brand as its default, and lasts one hour. No refresh token is issued:
the client sends a fresh assertion when the token expires, so removing a member
from the organization or the identity provider takes effect within the hour.
Scopes are the requested (or asserted) scopes that fit the connector's ceiling,
and `invalid_scope` is returned when none do.

The OAuth issuer and redirect URLs are derived from your public URL
configuration, so they must be reachable from the browser doing the sign-in.

## Create a brand from a URL

Organization owners and admins can call `setup_brand(action=onboard)` with
`input: { action: "create_from_url", url, label, approve }`: an HTTP or HTTPS
`url`, an optional `label`, and optional `approve` (default `false`). A
successful scan returns the brand id, revision id, draft or approved revision
status, completeness score, incomplete fields, and `reviewUrl`. Review the guide
at that URL before generating content. Set `approve: true` only when you want to
approve the guide in the same call.

URL checks time out after eight seconds and reject blocked destinations before
creating a brand. If processing takes more than twenty seconds after creation,
the response includes `brandId`, `reviewUrl`, and `scanStatus: running`. Poll
`get_context(action=brand_scan_status)` with that `brandId` for the current guide and completeness.
If voice analysis is unavailable, the completed response includes
`voiceAnalysis: unavailable`. Both calls are listed on every connection
and are available in agent chat. The scan uses the model provider keys you configured; see
[Provider API Keys](/self-host/provider-api-keys).

## Social accounts, brand scope, and media

Use `get_context(action=brands)` then pass `brandId` into generation and connection tools.
`brandId` is required on `generate_media(action=media)`, `generate_text(action=content)`, `generate_text(action=turbo)`,
`generate_text(action=enhance)` and `generate_media(action=transform)`, even when you own one brand: a call
without it returns `brand_required` and your brand list. Genfeed does not silently
pick a brand.

`setup_brand(action=connect_account)` returns a `connectionId` and a browser authorization URL.
Poll `check_channel(action=connection_status)` with that id. Provider denial or failure is stored
on that row immediately (`denied` / `failed`); do not wait for the 15-minute
expiry. Replay the same id after a client restart; it does not create another
credential.

An image `generate_media(action=media)` call returns structured artifact metadata plus a native image part when
the client supports it, with a text fallback. Video results are downloadable files
or open links; they do not claim inline playback. `selectedContext` is task-only
and is not saved as Knowledge.

The CLI equivalents are `gf connect <platform>`, `gf gen image --brand --context`,
and `gf status <id>`; see [CLI](/api-reference/cli).

## Avatar video and personal voices

`generate_media(action=media)` with `type: "avatar"` renders a talking-head video of the brand's
saved identity (its default avatar and voice). `prompt` is the topic Genfeed
writes a spoken script for; with `isVerbatim: true` it is spoken exactly as
written. `aspectRatio` defaults to `9:16`, and `voiceId` swaps the brand default
voice for a saved one. The call follows the [approval rules](#approvals) of other
paid generation, is billed per second of the rendered clip, and returns the Library
video id: poll it with `check_job(action=job)`.

Personal voices belong to the organization's own connected ElevenLabs account;
nothing falls back to a platform account.

- `get_assets` with `type: "voice"` lists the voices the organization saved
  (`isBrandDefault` marks the brand default). With `source: "account"` it browses
  the connected account (`q` searches, `pageToken` pages) and reports
  `connection.status`; a `disconnected` account returns no voices and says to
  connect it in Genfeed.
- `get_generation_catalog(action=options)` with `type: "voice"` returns the same saved voices and
  whether an account is connected.
- `setup_brand(action=generation_settings)` with `scope: "brand"` and `defaultVoice` (`voiceId`
  for a saved voice, or `externalVoiceId` to first save a voice from the
  connected account) makes the voice the brand default.

## Digital twin

A person can train a digital twin of themselves (an avatar plus a voice cloned
from the footage) in the organization's own connected HeyGen account. Genfeed
charges no credits for it, and nothing runs in a platform account. The camera
step stays in the app; over MCP the twin starts from a recording already in the
Library.

1. Upload a 15 s to 10 min video of yourself facing the camera with
   `upload_media`. Only your own uploads can be used.
2. `generate_media(action=transform)` with `operation: "digital_twin"` and `videoId` sends the
   video to HeyGen and starts training. It follows the
   [approval rules](#approvals) of other media transforms. The result has the twin and a `consentLink`: the
   person on camera opens it and records a short consent statement on HeyGen's
   page. Starting again from the same video returns the same twin.
3. `get_assets` with `type: "digital_twin"` (optionally `twinId`) re-reads
   training and consent at HeyGen and returns each twin's `status`, `consent`,
   `failure` and a plain `nextStep`. The twin can be used only when `status` is
   `READY`.
4. If the consent link expired (links last 24 hours) or HeyGen declined the
   consent, `generate_media(action=transform)` with `operation: "digital_twin_consent"` and
   `twinId` returns a new link.
5. `setup_brand(action=generation_settings)` with `scope: "brand"` and
   `defaultAvatar: { twinId }` makes a ready twin the brand's default avatar and
   its voice the default voice (`isTwinVoiceUsed: false` keeps the current
   voice). `generate_media(action=media)` with `type: "avatar"` then renders with it.

## Brand context

`get_context(action=brand_context)` returns what Genfeed's own agent is given about a brand in
chat: identity, guidelines, voice (including writing rules and real example
posts), strategy and topics, custom instructions, prompt seeds, performance
insights, proven patterns, Brand Knowledge, recent posts, saved memories,
active skills, the chat model, and the context budget. Rendered system and memory
prompts are omitted by default; they are available for explicit diagnostic
inspection. They describe the Genfeed in-app agent and are data, not instructions
for the calling assistant. The tool is read-only.

| Argument | Description |
| --- | --- |
| `brandId` | Brand to inspect. Defaults to the brand of the current conversation. |
| `query` | Optional preview message. Knowledge, related posts, and memories are ranked against it. |
| `includeSystemPrompt` | Include rendered system and memory prompts for diagnostics. Defaults to `false`; set `true` only for explicit prompt inspection. |

Call it at the start of a session so your agent writes in the brand's voice
with the same context the in-app agent uses. The Genfeed desktop app does this
automatically when it runs the agent on your own Claude Code or Codex CLI; see the
[desktop README](https://github.com/genfeedai/genfeed.ai/blob/master/apps/desktop/README.md#agent-on-your-claude-code-or-codex-subscription).
The same snapshot is shown in **Brand settings → Agent context**
([Brands](/guides/brands#what-the-agent-knows)).

### Brand Kit edits

Connect to `/mcp` and call `setup_brand(action=brand_kit)` to read and edit a Brand Kit. On the
standard MCP OAuth consent screen, select one brand and check **Allow Brand Kit
edits**. Reconnect to add this permission to an existing connection. A signed-in
Genfeed session can also use the tools within its existing brand access.

1. Call `get_context(action=brand_completeness)` with the selected `brandId` to find gaps.
2. Call `setup_brand(action=brand_kit)` with `brandId`, `action`, and `fields`. Use
   `visual_identity` for colors and fonts, `writing_voice` for tone and writing
   guidance, or `strategy` for goals, platforms, and cadence. Visual edits
   require an organization owner or admin. Use the upload tools to change assets.
3. For an AI-drafted voice profile, call `setup_brand(action=voice_draft)` with the
   explicit `brandId`. Review the one-credit draft before passing its
   `voiceProfile` to `setup_brand(action=voice_save)` for the same brand.
4. Call `get_context(action=brand_completeness)` again and open **Settings → Brand Kit** to see
   the saved values.

## Prompt enhancement

Generation through MCP uses the same prompt enhancement as Studio and the
in-app agent. It is **on by default** for image and video, and it applies the
brand's guidelines plus any hosted harness packs.

**It is never silent.** Every `generate_media(action=media)` result says what was sent to the model:

- the result text shows `Prompt enhancement: applied` or `skipped`, the setting
  it followed (`default`, `organization setting`, `brand setting` or `this call`),
  the exact prompt sent, your original prompt, and the applied pack IDs and
  versions;
- `structuredContent.data.generationHarness` carries the full receipt:
  `originalPrompt`, `enhancedPrompt`, `status`, `source`, `brandId` and
  `appliedPacks`. Read it when your client shows only structured data.

If enhancement is on and fails, the call stops before any provider is billed.
It does not fall back to your raw prompt.

**Turn it off for one call** with `harness: false` on `generate_media(action=media)`. The provider
then receives your prompt unchanged and the result reports `skipped`.
`harness: true` forces it on for that call.

**Change the default** with `setup_brand(action=generation_settings)`: `scope` is
`organization` or `brand` (a brand also needs `brandId`), and `isEnabled` is
`true`, `false`, or `null` to reset to inherit. A call overrides the brand,
a brand overrides the organization, and the organization overrides the default
(on). `get_generation_catalog(action=options)` with a `brandId` shows the effective setting and
where it came from. Changes show up in the app's **Prompt enhancement settings**.

**Preview before you spend.** `generate_text(action=enhance)` returns the enhanced prompt
without creating media. Pass that text to `generate_media(action=media)` with `harness: false` to
submit exactly what you reviewed.

Client skills such as `image-prompt-engineer` stay optional. If one already
rewrote your prompt, send `harness: false` so it is not enhanced twice.

## Presets

The presets you see in Studio and the Storyboard are readable over MCP. Both
tools are read only: nothing is generated and no credits are spent. They are in
`get_generation_catalog(action=presets)` and `get_generation_catalog(action=preset)`.

- `get_generation_catalog(action=presets)` lists presets with a key, kind, label and description. `kind` is
  `image`, `image-edit`, `video`, `storyboard`, `ad`, `playbook` or
  `cinematic-short`. Pass `kind` or `search` to narrow the list.
- `get_generation_catalog(action=preset)` reads one preset by key. For a `cinematic-short` it returns the
  slots to fill and a worked example. Pass `slots` (and optionally `brandName`)
  to also get the compiled prompt, the timed shot plan in whole frames, the
  negative prompt and the sound spec. Slots are only compiled for cinematic
  shorts.

Pass the compiled prompt to `generate_media(action=media)`. Approval and credits stay on that call.

## Publishing readiness

Before scheduling, call `check_channel` with `action: capabilities` and
`check_channel(action=readiness)` for the selected brand. A connected account
alone does not make its channel schedulable. Readiness combines credential
health with the canonical scheduler capability catalog.

A `supported` channel retains its credential and setup checks. A `hidden`
channel has a backend integration but cannot be scheduled until live publishing
is verified; a `planned` channel has no available scheduling path. Both return
`canSchedule: false`, `state: "blocked"`, and a
`scheduler_channel_unavailable` diagnostic. Uncatalogued channels also fail
closed. Existing token, permission, and setup diagnostics remain available.

A Facebook connection is one Page. Connecting an account that manages several
Pages asks which Pages to use, and each chosen Page is its own channel. A
connection that has no Page (an account made before Pages were chosen, or one
used only for Meta Ads) cannot publish: reconnect and choose a Page. A Facebook
post takes one photo or one video.

## Tool errors

A gating failure is a tool result with `isError: true`. `structuredContent`
is the contract below, not a generic 500 and not a bare string. The same
object is `error.data` on the JSON-RPC response when the Streamable HTTP
transport rejects the request before a tool runs (missing credential, or the
shared `RateLimitService` window). JSON-RPC `error.code` stays numeric.

| `code` | When | `nextStepUrl` | Extra fields |
| --- | --- | --- | --- |
| `unauthorized` | Missing or rejected bearer credential (`401`) | `/connectors/agents` on your app origin | |
| `rate_limited` | `RateLimitService`, or an upstream `429` | none | `retryAfterSeconds` when the limiter reported a wait |
| `validation_failed` | REST `ValidationPipe` / `ErrorResponse.validationFailed` field errors, or a missing required tool argument | none | `errors[]` of `{ field, message }` |
| `approval_pending` | `mutationPolicy: 'approval-required'` queued the write instead of running it | `/publishing/approvals` | `approvalId`, `toolName`, `approvalStatus`, `canResolveApproval` |
| `confirmation_required` | A publishing call (dated release, release update, `publish-now`, `resume`, article publication) without `confirmed: true`; nothing ran and no approval was queued | none | `toolName` |
| `brand_required` | A generation tool (`generate_media(action=media)`, `generate_text(action=content)`, `generate_text(action=turbo)`, `generate_text(action=enhance)`, `generate_media(action=transform)`) was called without `brandId` | none | `brands[]` of `{ id, label }`, the caller's brands |

`message` is always set. `retryAfterSeconds` and `nextStepUrl` are omitted
when they do not apply; `rate_limited` does not invent a URL. Paths are app
routes on your instance; sign-in continues into the caller's organization. Fix
`errors[]` and call the tool again. For `approval_pending`, hand the human
`nextStepUrl` or, when `canResolveApproval` is true and the user approves, call
`resolve_approval` with `structuredContent.approvalId`. For
`brand_required`, retry with one of the listed `brands[].id` values; no brand is
ever picked for you.

## Approvals

"Require approval for MCP requests" is off by default for every organization and
member, so credit-spending calls such as `generate_media(action=media)` run straight away. An owner
or admin can turn it on in Settings, Organization, and a member can turn it on
for themselves in Settings, Personal. A call waits in the approvals queue as soon
as either switch is on. Credit balance checks and quotes always apply, and
sending messages, replies and outreach always wait for approval, whatever these
switches say.

Publishing never uses the web approvals queue. `schedule_release` (a dated
release, or an update to one), `control_release` (`publish-now`, `resume` and
`publish`) and article publication are confirmed with the person in the
conversation. The first call changes nothing and returns `confirmation_required`;
the agent shows the person what will go out, and repeats the same call with
`confirmed: true` only after they agree. Release drafts, `cancel` and `pause`
need no confirmation.

Deleting works the same way. `control_release(action=remove_post)` deletes a
post from Genfeed, a published one included, and with `deleteMedia: true` the
Library media only that post uses; `control_release(action=remove_asset)` deletes one
Library asset. Both return `confirmation_required` until the person agrees and
the agent repeats the call with `confirmed: true`. By default they delete in
Genfeed only: a post that went out stays live on its social network until its
owner deletes it there, and the result says so (`deletedOnPlatform: false`).
With `deleteOnPlatform: true` `remove_post` deletes the post on its network
first, on X and Mastodon; any other platform is refused, and when the network
refuses nothing is deleted at all. The result also
reads the post and media back, and the agent confirms with `get_content` and
`get_assets`. The Claude connector at `/mcp/claude` does not list them. The CLI
has `genfeed posts delete <id> [--with-media] [--on-platform]` and `genfeed asset delete <id>`,
each asking for confirmation unless `--force` is given.

## Tools

Each call uses the permissions on the authorized token or key.

- **Content and media:** articles, images, videos, music, avatars, Turbo runs.
- **Workflows:** list, create, execute, inspect status.
- **Publishing:** list and publish social posts.
- **Analytics and ads:** analytics, campaigns, Google Ads, Meta Ads.
- **Agents and admin:** threads, approvals, role-gated admin tools.

Generation tools call the model providers whose keys you configured; see
[Provider API Keys](/self-host/provider-api-keys).

## Tools and organizations

Every connection lists the same tools, at most 30 for an ordinary user (the
list is checked in CI). Nothing needs selecting: `?toolsets=`, `?profile=` and
`?app=` are no longer read, and an old URL that still carries them connects and
gets the same list. The Claude connector at `/mcp/claude` keeps its fixed,
smaller list.

Most tools take an `action` and one `input` object, so one tool covers a family
of operations. Permissions and approvals are checked on the call, whatever is
listed.

| Tool | Actions |
| --- | --- |
| `get_context` | `account`, `brands`, `organizations`, `brand_context`, `brand_completeness`, `brand_scan_status` |
| `setup_brand` | `onboard`, `interview_*`, `connect_account`, `connect_oauth`, `brand_kit`, `voice_draft`, `voice_save`, `generation_settings` |
| `generate_text` | `content`, `turbo`, `repurpose`, `enhance` |

### Several organizations on one connection

A connection can cover several organizations (the OAuth consent screen offers
**All organizations**). Such a connection has no default organization:

- Call `get_context(action=organizations)` to list the organizations with their
  ids, slugs and brands.
- Every other tool takes an `organization` argument (name, slug or id). A call
  without it is refused with `organization_required` and the same list. Pass it
  together with the `brandId` of that organization's brand.
- A result that creates or changes something names the organization and the
  brand it acted in, and approvals show both.
- `find_tools`, `resolve_approval` (listed on admin connections only) and
  `get_context(action=organizations)` do not need it.
- A connection limited to one organization works inside it. Leave `organization`
  out there; naming one is refused.

### Workspace review and tasks

`get_workspace(action=review_queue)` and `manage_workspace(action=task)`:

- `get_workspace(action=review_queue)` returns the ready Turbo items from the latest visible batch
  and the pending workflow gates and MCP approvals from Publishing → Approvals.
  Pass `brandId` to choose a brand or `turboRunId` to inspect another visible batch.
  Batch queries support an optional item `status` filter. Review decisions stay
  in Genfeed.
- `manage_workspace(action=task)` takes an `input` containing `taskId` and an `action`.
  Use `update` to change task fields such as `status` or `assigneeUserId`,
  `comment` with a Markdown `body`, or `complete` to move the task to Done
  through the same status rules as Workspace → Tasks.

### Saved remix handoff

Imported-post remix uses `save_remix` and `run_remix`, which every connection lists.

Call the actions in this order. Saving, importing, reading, editing, attaching,
and quoting never dispatch generation, publish, or add brand Knowledge.

1. `save_remix(action=import_source)`: public X, Instagram, or TikTok URL plus explicit
   `brandId`. Approval is required. Unsupported, private, or missing inputs fail
   closed. The result is the imported source identity and whether it was reused.
2. `save_remix(action=concept)`: `brandId` and `sourcePostId`. Creates or reuses the
   canonical saved concept and returns its current revision.
3. `save_remix(action=concept_update)`: `runId`, `expectedRevision`, and at least one edit.
   A stale revision fails instead of overwriting.
4. `save_remix(action=attach_source)`: optional, for video or avatar output.
   Pass a same-brand Library video id, or `null` to clear it. The Library video
   is the analyzed media. The imported post URL, author, and selector stay
   provenance.
5. `run_remix(action=quote)`: persists an exact quote for `expectedRevision`
   and does not start work. Read it back with `run_remix(action=status)` before approval.
   Image and copy accept only `operation: "generate"` and reject scene or repair
   fields. Image requires a registered image `model`; `crun/` models do not
   support remix quotes and are rejected. Copy rejects a caller `model` and uses
   the canonical background model. Video and avatar reject `model` and quote
   `analysis`, `generate`, or `repair` on the scene pipeline. A quote expires 15
   minutes after it is saved. Provider, model, BYOK, source, or recipe changes
   require a new quote.
6. `run_remix(action=start)`: approval-required. Pass the persisted `quoteId`
   and the same revision. A repeated accepted call returns the same canonical
   run and does not start the attempt again.
7. `run_remix(action=status)`: safe reconnect. Returns revision, lineage, quotes, receipts,
   and artifacts without starting another run.
8. `run_remix(action=control)`: approval-required `cancel` or `resume` for an
   existing video or avatar scene pipeline. Image and copy have no control
   action.

Image and copy execute through the generic generation quote. Video and avatar
execute through the scene pipeline. Single-scene legacy video or avatar start
is not an unquoted shortcut. Live native-client acceptance, paid provider
calls, and real publishing are not claimed here.

### Discover a tool

The read-only `find_tools` takes `{ name?, query?, limit? }`:

- **No arguments**: every tool this connection lists, with its actions.
- **`query`**: case-insensitive substring search over tool name, description and
  action name. A retired tool name finds the tool that replaced it.
- **`name`**: the full definition of one tool, including the closest name
  matches when the name isn't found.

Discovery returns descriptions; it does not install a tool into the client's
callable tool list. If the client cannot call a listed tool, refresh its MCP
tool list or reconnect to the same server URL.

## Skills

MCP gives an agent Genfeed's tools; [Agent Skills](/skills) give it the content
knowledge to use them well. Install the catalog with
`bunx skills add genfeedai/skills`.

## Add Library media to generated copy

1. Select a brand with `get_context(action=brands)`. Call `generate_text(action=content)` for social copy.
   It saves a reviewable draft and returns `postId`, `content`, and `receiptId`
   in `structuredContent.data`.
2. Find a hosted Library image or video URL with `get_assets` or `upload_media`.
   Call `save_post(action=post)` with the returned `postId`, the same `brandId`, and the
   URLs in `mediaUrls`. This updates the original draft's media in the order
   supplied and keeps its text, title, visibility, and generation receipt.
3. Call `get_content(action=posts)` with the same `postId` to read back the draft, including
   its media and `receiptId`. Retrying the attachment updates the same draft.

If the draft is unavailable to edit or the media fails validation, the call
fails. Omit `postId` to create a new draft from supplied text or Library media.

## Uploading local media

Every connection lists `upload_media` and `get_content(action=posts)`. Select a brand before reserving an upload.

1. Call `upload_media` with `action: request` and `input: { filename, contentType, category }`.
2. Upload to the returned `uploadUrl` before it expires. For `method: PUT`, send
   the file bytes with the returned headers. For self-hosted `method: POST_JSON`,
   send the returned `localUpload` object as JSON, adding the base64-encoded file
   bytes as `localUpload.source.data`. Respect the returned file constraints.
3. Call `upload_media` with `action: complete` and `input: { assetId }`. Its `media` entries
   can be passed to `schedule_release(action=create)`; a returned hosted `url` can also
   be used in `save_post(action=post)` `mediaUrls`. Scheduling retains its approval checks.
4. Use `get_content(action=posts)` with `postId` to read a post's targets, state, media, and timestamps.

Upload reservation creates a pending asset. Both upload actions are non-destructive
writes; `get_content(action=posts)` is read-only. None of these tools publishes a post.

## Interactive content cards

MCP Apps hosts can render Genfeed content directly in the conversation:

- **Content calendar:** `get_content(action=posts)` with `days`, shown as one column per day, with open days and the drafts count.
- **Post previews:** platform, status, copy and media. Generated caption variations appear once each in a responsive grid; a single result keeps one card.
- **Images:** compact previews with expand and open controls; metadata stays out of the primary view.
- **Video and audio players.**
- **Running generations:** a progress state that re-reads `check_job(action=job)` until the media is ready.
- **Article cards.**

Account lookups return a readable message with setup status, role, credits, and
requested usage metrics. They do not open a content widget. Tool text contains
readable summaries; internal identifiers and complete payloads remain in
`structuredContent.data` for follow-up calls. Clients should read structured
fields rather than parse display text as JSON. Errors provide readable guidance
and keep their error codes and approval references in `structuredContent`.

The MCP server serves a self-contained HTML resource at
`ui://genfeed/content-cards-v5-<content-hash>.html` with MIME type
`text/html;profile=mcp-app`. Selected tool descriptors link it through
`_meta.ui.resourceUri`. They also carry the legacy `ui/resourceUri` key and the
ChatGPT `openai/outputTemplate` alias. The widget uses the standard MCP Apps
JSON-RPC bridge, and its only tool call is the read-only `check_job(action=job)`.
The resource bundles Genfeed's shared Card, Button, Badge, typography, media
players and Dialog components with the product stylesheet and Satoshi served from the MCP origin. Its content
hash changes when shared UI, styles or the font change, invalidating host caches.
No separate ChatGPT frontend deployment is needed.

Text and media resource links remain available to clients without MCP Apps.
Empty results and tool errors remain visible, and pending approvals are never
presented as completed content. Cards do not publish or mutate content.

Configure `GENFEEDAI_CDN_URL` and, if media is served directly by it,
`GENFEEDAI_MICROSERVICES_FILES_URL` on the MCP server; see
[Configuration](/self-host/configuration#public-urls). Only these media origins
are allowed by the widget CSP. Other HTTP(S) media URLs remain available through
an explicit open-link action. The static HTML resource is public; all account
data still comes from authenticated tool calls. It contains no bearer tokens or
account cookies.

## Claude, Claude Code and Cowork

Connect to `http://localhost:3014/mcp/claude` with browser OAuth (see
[Claude Code](#claude-code) above). This connector supports brands, drafts,
existing assets, scheduling and analytics. It does not generate media. To
generate images, video and audio from a Claude client, add the standard
endpoint (`http://localhost:3014/mcp`) as a second custom connector; it
authorizes separately and carries the generation tools.

This is a custom connector; Genfeed is not yet submitted or published in the public Claude directory.
Existing connections to `/mcp` retain their original capabilities.

The restriction is bound to the OAuth resource, persists across token refresh and is enforced on execution and discovery. Using the Claude token on `/mcp` does not enable generation; a separate connection to `/mcp` has its own grant. Workflows, Turbo runs, remix, arbitrary agent calls and approval redemption are unavailable through this connector. Other clients use the standard `/mcp` connector.

## Troubleshooting

- **Discovery fails:** use exactly your MCP URL (`http://localhost:3014/mcp` on a default install) and a Streamable HTTP client.
- **401 errors:** an OAuth client should present its refresh token first and
  restart browser authorization only if that fails; with an API key, check the
  key and its scopes.
- **Wrong endpoint:** check `/v1/config` on the MCP host.
- **Cannot connect at all:** confirm port `3014` is published; see
  [Troubleshooting](/self-host/troubleshooting).
