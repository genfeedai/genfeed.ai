# Installation Options

There are three ways to run Genfeed. Most people should pick the first or second:
both start the same published release as a single container next to PostgreSQL,
and neither needs a repository clone.

| Option | Best for | Needs |
| --- | --- | --- |
| [`npx @genfeedai/create`](#option-1-npx-one-command) | The fastest start | Docker Compose v2, Node.js 24 |
| [Release bundle](#option-2-release-bundle-with-docker-compose) | Servers, CI, or machines without Node.js | Docker Compose v2 |
| [From source](#option-3-from-source-contributors) | Contributors changing Genfeed itself | Node.js 24, Bun, Git, Docker Compose v2 |

Check the [system requirements](/self-host/system-requirements) first. Plan on about
10 GB of free disk (15 GB recommended), and free ports `3000`, `3010`, and `3014`.

Whichever option you pick, you configure the instance with one `.env` file of
environment variables. After you edit it, recreate the stack
(`docker compose --env-file .env -f compose.yml up -d`); a plain `restart` does
not re-read `.env`. When something looks wrong, start with
`docker compose --env-file .env -f compose.yml logs genfeed`, and see
[Troubleshooting](/self-host/troubleshooting).

**Before you start:** have an [OpenRouter key](/self-host/provider-api-keys) ready.
You can start the stack without it, but the first text generation fails until it
is set.

## Option 1: `npx` one command

```bash
npx @genfeedai/create my-genfeed
```

This downloads the release bundle, verifies its checksum and manifest, validates
the Compose file, and starts it with Docker Compose.

It needs Node.js 24 (`>=24 <25`). On any other Node version, use the release
bundle below. `@genfeedai/create` is separate from the
[`@genfeedai/cli`](/api-reference/cli) terminal client, which needs Node.js
22.12 or newer.

## Option 2: Release bundle with Docker Compose

The release bundle is a checksummed tarball of the latest stable release. It
runs as one container alongside PostgreSQL, so there is no git clone and no
build step.

```bash
curl -fLO https://github.com/genfeedai/genfeed.ai/releases/latest/download/genfeed-selfhosted.tar.gz
curl -fLO https://github.com/genfeedai/genfeed.ai/releases/latest/download/genfeed-selfhosted.tar.gz.sha256
sha256sum -c genfeed-selfhosted.tar.gz.sha256
tar -xzf genfeed-selfhosted.tar.gz
cd genfeed-selfhosted-v*
cp .env.example .env
docker compose --env-file .env -f compose.yml up -d
```

On macOS, use `shasum -a 256 -c genfeed-selfhosted.tar.gz.sha256` for the
checksum step.

The bundle contains `compose.yml`, `.env.example`, and a manifest. The manifest
and Compose file pin the exact application image for that release. On first
boot the container applies database migrations and seeds one local user, one
organization, and one brand. The default configuration has sign-up and
sign-in turned on, so you create your own account on first visit.

### Open it

| Surface    | Address                 |
| ---------- | ----------------------- |
| Web UI     | `http://localhost:3000` |
| REST API   | `http://localhost:3010` |
| MCP server | `http://localhost:3014` |

PostgreSQL is reachable only inside the Compose network, and Redis runs inside
the Genfeed container. Neither is published on a host port.

Confirm that the API process responds:

```bash
curl http://localhost:3010/v1/health
```

This is a process-level check. It does not prove that the database, queues, or
any model provider are ready.

### Create the first user

How you get in depends on one setting, `BETTER_AUTH_ENABLED`. These steps were
read from the code and have not been run end to end on a clean install, so tell
us if something differs.

**Optional no-login mode (`BETTER_AUTH_ENABLED=false`):**
Open `http://localhost:3000`. The first boot seeded one local user
(`admin@localhost`, which has no password), one organization with the slug
`default`, and one brand. The web UI opens as that user, so anyone who can reach
it has full access. The API accepts tokenless local identity only from loopback
or Docker-network peers, and its host port binds to `127.0.0.1`. Keep no-login
installations on your own machine or behind your network's access controls.

**Default, with the login wall (`BETTER_AUTH_ENABLED=true`):**

1. Keep the switch enabled in `.env`, then recreate the stack if you changed it. The container entrypoint
   reads it at start, and makes the browser-side `NEXT_PUBLIC_BETTER_AUTH_ENABLED`
   follow it, so a plain restart is not enough. Setting both to `true` is fine:

   ```env
   BETTER_AUTH_ENABLED=true
   NEXT_PUBLIC_BETTER_AUTH_ENABLED=true
   ```

   `BETTER_AUTH_SECRET` can stay empty: the container generates one and keeps it
   in `/data/.better-auth-secret`.
2. Create your account. The login page offers **Google** and **Magic Link**
   only. Both need setup: Magic Link needs `RESEND_API_KEY` to send the email,
   and Google needs `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET`.
   With neither configured, create an email and password account through the
   API instead:

   ```bash
   curl -X POST http://localhost:3010/v1/auth/sign-up/email \
     -H 'Content-Type: application/json' \
     -d '{"name":"Your Name","email":"you@example.com","password":"a-long-unique-password"}'
   ```

   Email verification is skipped on a self-hosted install with no mailer, so the
   account works immediately. If you add `RESEND_API_KEY` later and verification
   is switched on, new accounts must verify by email.
3. Sign in at `http://localhost:3000/login/password` with that email and
   password.

What to expect:

- The new account gets its **own** organization and brand. It does not take over
  the seeded `default` workspace, and `admin@localhost` has no password, so you
  cannot sign in as it.
- With the login wall enabled, protected API requests on port `3010` need a
  valid session token or API key, even from loopback. The API host port binds to
  `127.0.0.1`; keep the login wall on before exposing it through a
  [reverse proxy](/self-host/reverse-proxy). MCP on `3014` always needs its own
  bearer credential.
- If sign-in fails behind a custom domain, set `BETTER_AUTH_URL` and
  `BETTER_AUTH_TRUSTED_ORIGINS` to your public API and app URLs. See
  [Configuration](/self-host/configuration#login-wall).

### Add your own keys

Self-hosted Genfeed has no Genfeed credits. **Add an OpenRouter key before your
first generation:** set `OPENROUTER_API_KEY` in `.env` to a real key, and
recreate the stack. Without it, text generation fails with
`Missing provider key: OPENROUTER_API_KEY`. Other keys are optional. See
[Provider API keys](/self-host/provider-api-keys).

### Source checkout Compose file

A repository checkout also contains `docker/docker-compose.selfhosted.yml`. It
is configuration for contributors: it still runs a published image and does not
build your checked-out code. Unlike a release bundle, its template defaults to
the mutable `latest` image tag unless you set `GENFEED_IMAGE_TAG`.

## Option 3: From source (contributors)

Use this path only if you are changing Genfeed itself. To run Genfeed, use option 1 or 2.

### Requirements

- Node.js `>=24 <25`
- Latest stable Bun (see `.bun-version`)
- Git
- Docker Engine with Docker Compose v2, for local PostgreSQL 17 and Redis 7
- A C/C++ toolchain and `python3`, because `bun install` compiles the `node-pty`
  native module:
  - Debian/Ubuntu: `sudo apt-get install -y build-essential python3`
  - macOS: `xcode-select --install` (Xcode Command Line Tools)
- systemd on Linux, because `bun run dev:setup` installs the Portless HTTPS
  startup service

See the [contributor prerequisites](https://github.com/genfeedai/genfeed.ai/blob/master/CONTRIBUTING.md#prerequisites-by-platform)
for the full per-platform setup.

This repository is Bun-only. npm, Yarn, and pnpm installs can produce an
unsupported dependency tree.

### Set up the workspace

```bash
git clone https://github.com/genfeedai/genfeed.ai.git
cd genfeed.ai
bun install
cp .env.example .env.local
```

Before syncing the environment, edit `.env.local` and set at least the local
database credentials used by `docker/local/docker-compose.yml`:

```env
DATABASE_URL=postgresql://genfeed:genfeed_local@localhost:5432/genfeed
REDIS_URL=redis://localhost:6379
```

Then generate workspace environment files and start the dependencies:

```bash
bun run env:sync local --prune-legacy
docker compose -f docker/local/docker-compose.yml up -d postgres redis
```

Install the Portless HTTPS startup service once per machine (idempotent; it may
request administrator approval to bind port `443` and trust the local CA):

```bash
bun run dev:setup
```

Verify with `bun run dev:doctor`. Interactive development uses clean HTTPS
routes such as `https://app.genfeed.localhost`, not fixed ports.

Run the minimum backend and the app in separate terminals:

```bash
bun run dev:backend:min   # api + files + notifications
```

```bash
bun run dev:app           # https://app.genfeed.localhost/
```

Other common entry points:

| Command | Starts |
| --- | --- |
| `bun run dev` | Full stack (app + backend + docs + website) |
| `bun run dev:backend` | Full backend (+ mcp + workers) |
| `bun run dev:docs` | Docs site |
| `bun run dev:debug:*` | Fixed-port debug only (explicit) |

Use the scripts in the root and workspace `package.json` files rather than
inventing service commands. Source-development Prisma migrations run through:

```bash
bun run --cwd packages/prisma db:migrate
```

See the
[contribution guide](https://github.com/genfeedai/genfeed.ai/blob/master/CONTRIBUTING.md)
for focused checks, Portless hosts, and pull-request requirements. Report
suspected vulnerabilities through the
[security policy](https://github.com/genfeedai/genfeed.ai/security/policy), not a
public issue.
