**Steadier**
- The API logs one JSON line per entry in production, which is cheaper per request. The short request stalls are still being traced; this is a mitigation, not a proven fix.
- Media URL signing in the API does its database and RSA work once per request instead of repeatedly, concurrent cache misses join one load, and the marketing build cache is shared. A boot heap budget in CI fails a change that grows the API's startup heap.
- The API's Prisma client holds far less memory (the generated parameterization graph shrank from 83 to 9 MB), and cross-post pairing no longer scans more than it needs. Together with the lazy SDK loads, this targets the memory stalls in #10110; whether it removes them is read after the deploy.
- The API's server keep-alive is 65 s, above the 60 s load balancer idle timeout. The googleapis and ElevenLabs SDKs load on demand, which takes about 100 MB off the startup heap (325 to 221 MB). Every full garbage collection is logged with its stall, so the next check reads the real numbers.
- The API task runs at 2 vCPU and 4 GB instead of 1 vCPU and 2 GB, to test whether the 1 vCPU quota causes the request stalls. It is reverted if stalled requests per day do not fall by at least half after the deploy.
- The app stops error replay recording and reports DOM growth when a tab passes 768 MiB, to find the approvals page crash. Also a mitigation, not a proven fix.
