# Argil Avatar Video Model Decisions

GitHub issue: #2849

**Why:** Argil overlaps with HeyGen at the avatar-video boundary but has a project-and-render API that does not match generic cinematic video generation.
**How to apply:** Add one dedicated adapter and one complete Clip Studio path; retain the current default and reuse existing completion/media boundaries.

## Chosen Approach

Implement `argil/atom` behind `AvatarVideoProvider` and expose it as an additive Studio Clips provider. The adapter creates a one-moment Argil video, starts its render, and correlates the Argil video ID with the existing clip result. A dedicated authenticated callback maps terminal Argil events into the same clip reconciliation used by HeyGen.

This is the smallest coherent production path: the key can be configured, the model can be selected, generation can be dispatched, and the final media can reach Genfeed storage and the clip project.

## Alternatives Considered

1. **Generic video-generation adapter.** This would make Argil appear beside Kling, Veo, and other cinematic models, but the current generic contract has no avatar or voice identity. Adding those fields would leak avatar-specific semantics into every video provider.
2. **Replace or wrap HeyGen.** This would reduce visible provider choice, but violates the requirement that Argil is complementary and creates migration risk for existing HeyGen identities and workflows.
3. **Full Argil platform integration.** Catalog management, avatar training, B-roll, captions, music, and story editing are useful later, but they expand the first production test beyond the requested model pipe.
4. **Selected: dedicated additive avatar adapter.** This matches the existing provider seam, keeps the blast radius bounded, and leaves room for later Argil capabilities without pre-committing the generic video architecture.

## Model Decision

Register only `argil/atom`. Argil's public API exposes both `ARGIL_ATOM` and legacy `ARGIL_V1`; Atom is the current model and avoids exposing a second untested choice. The model capability advertises only `16:9` and `9:16`.

## Credential Decision

Argil is a `ByokProvider`, not a `CredentialPlatform`. Social credential enums remain reserved for publishing destinations. The service resolves organization BYOK first and then `ARGIL_KEY` for self-hosted/operator deployments.

## Completion Decision

Use Argil's per-render callback rather than a permanent account webhook. Argil's public docs do not define a delivery signature, so Genfeed supplies a per-video HMAC token derived from the Argil video ID and `ARGIL_WEBHOOK_SECRET`. The callback verifies the token with constant-time comparison and then verifies that the local target's stored provider job ID matches the payload.

This token proves the callback URL was generated by Genfeed without exposing the server secret. Terminal-state checks make retries idempotent. `GET /videos/{id}` remains available through the adapter for diagnostics and future polling fallback.

## Persistence Decision

No Prisma migration is required for the first slice. Clip results already store string `providerName` and `providerJobId`; BYOK keys live in the existing organization-settings JSON boundary. Model registration uses constants rather than a new database enum.
